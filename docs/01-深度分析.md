# 四个 VPN 样本的静态逆向：架构、协议栈与节点来源

样本日期 2026-11-12。全部结论来自 APK 静态分析（dex 字符串池 + const-string 引用反查 + ELF 导出符号 + 资源解密实测），
未使用模拟器与动态抓包。

## 0. 结论速览

| # | 文件 | 真实包名 | 隧道内核 | 节点来源 | 本轮能否直接产出可用代理 |
|---|---|---|---|---|---|
| 1 | ExpressVPN v12.71.0 (PREMIUM).apk | `com.free.vpn.super.hotspot.open` | Xray + OpenVPN + IKEv2 + Trojan | 账号体系下发 | 否，需账号态 |
| 2 | Proxy Master v5.4.5 (Premium).apk | `com.free.vpn.proxy.master.app` | sing-box + 私有 TLS+ | AllConnect 初始化接口 | 否，密钥在 native |
| 3 | VPN Proxy Master v2.3.6 [Premium].apk | `com.vpnmasterx.fast` | OpenVPN3 / OpenVPN2 | protobuf 下发 | 否，密钥在 native |
| 4 | VPN v206 (Premium).apk | `com.starnest.vpnandroid` | ICS OpenVPN | 配置下发 | 否，API 主机未定位 |

四个样本**没有任何一个**在包内静态携带可直接使用的标准协议节点（ss/vless/vmess/trojan/hysteria 链接）。
这与本仓库此前 FastVPN / EdgeVPN / MistyVPN 那批"接口直接吐订阅"的样本是两类东西。

## 1. 身份辨认：文件名不可信

`ExpressVPN v12.71.0 (PREMIUM).apk` **不是** ExpressVPN。真实 ExpressVPN 的包名是 `com.expressvpn.vpn`。
这个包的 `package=com.free.vpn.super.hotspot.open`，内部命名空间是 `com.superunlimited.*`，
官网域名 `vpnsuper.com`，品牌是 **SuperUnlimited VPN**。文件名是分发渠道套的壳。

另外三个的包名与文件名基本对得上，但同样都是白标贴牌产品：

- `com.free.vpn.proxy.master.app` 内部是 `com.hotspot.vpn.allconnect.*` + `com.free.connect.*`，即 **AllConnect VPN SDK** 白标。
- `com.vpnmasterx.fast` 内部是 `com.vpnmasterx.*`，`networklib` 包结构完整。
- `com.starnest.vpnandroid` 内部是 `com.starnest.*`，除 VPN 外还打包了 photo vault、浏览器、moreapp，是工具合集型模板。

## 2. com.free.vpn.super.hotspot.open（名义 ExpressVPN）

```
versionName 12.71.0 / versionCode 22802 / minSdk 26 / targetSdk 35
dex 6 / .so 19
```

隧道内核是四套并存，从 `lib/arm64-v8a/` 的导出符号可以逐一定位：

| 库 | 判定 |
|---|---|
| `libv2ray.so` + `libgojni.so` | Xray/V2Ray（Go），`libgojni` 里可见 `clash.Clash_start`、`v2rayPoint.setConfigureFileContent` |
| `libopenvpn.so` + `libopvpnutil.so` + `libjbcrypto.so` | ICS OpenVPN 系（`de.blinkt.openvpn.core.NativeUtils`） |
| `libcharon.so` + `libipsec.so` + `libstrongswan.so` + `libandroidbridge.so` | StrongSwan IKEv2 |
| `libtrojan.so` | `com.superunlimited.feature.vpn.superproto.JNIHelper_start/stop` |
| `libtun2socks.so` | tun2socks |

`res/raw/china_clash_config.yaml` 是本地 socks5 模板（`server: 127.0.0.1` / `port: 1081` 均标注 *port will be replaced*），
不是节点表。`assets/custom_routing_black|white|global` 是 Xray 路由规则 JSON（`outboundTag` / `domain` / `port`），
同样不含节点。

节点相关的静态资产有两组：

- `assets/open_readme`（2796 B）——**已解密**，见第 5 节。
- `assets/server`（155552 B）与 `assets/server_files/server{,_BD,_EW,_IN,_IR,_JO,_MM,_PK,_RU,_VN}`（12 KB–225 KB）。
  这十个文件 base64 解码后熵 8.00、无重复块、长度 ≡ 8 (mod 16)，用已还原的 `EasyVPNIKEV2Open` 密钥
  AES-ECB/CFB 均不成立，说明是**另一套密钥/算法**。dex 里不存在 `server_files` 字面量，
  即 Java 层从未以该路径打开过资产——它们要么由 native 读取，要么是历史残留。

账号侧：`https://account.vpnsuper.com/`、`https://account.getsuperulimited.com/`（厂商自身拼写如此）、
`https://account.vpnsuper.site/` 三个基址硬编码在 `classes.dex`。实测三者都是**网页账号门户**（307 → `/en/`），
不是节点接口。`classes4.dex` 的 `LSa/b`（`TvSignInSignUpFlowAPI`）是登录/注册流程。

结论：这套 App 的节点依赖登录态，静态侧只能拿到模板与加解密原语，拿不到节点集合。

## 3. com.free.vpn.proxy.master.app（Proxy Master 5.4.5）

```
versionName 5.4.5 / versionCode 545 / minSdk 24 / targetSdk 35
dex 8 / .so 16（含 libbox.so 28 MB = sing-box）
```

数据模型是本批样本里最完整的，全部在 `classes4.dex` 的 `com.hotspot.vpn.allconnect.bean`：

```
InitResponse
  ├─ location : LocationDTO { free: List<LocationBean>, vip: List<LocationBean> }
  ├─ protocols : Map
  ├─ retCode / ping / minVersion / suggestVersion / promoList / updateBean
LocationBean  { locationId, locationName, countryCode, nodeType, pingAddr, info, vip, delay }
NodeBean      { serverId, host, port?, country, locationName, alisaName, proxySelf,
                protocolConfigMap, modeConfigMap, auto, delay }
NodeResponse
```

取数链路（`classes5.dex`）：

```
Lg5/b.a()  ->  MMKV 键 "llll11llll11_2450"
             -> 若空: Lc5/f.a()
                  -> FirebaseRemoteConfig.getString("supertop_api_config")
                  -> 若空: Lf5/b.l("ras", app)   // res/values 里名为 ras 的字符串
             -> Lcom/hotspot/vpn/tls/TlsPlusManager;->f(Context, String) 解密
             -> JSON.parseObject(..., ApiConfig.class)
ApiConfig { apiList, keyApiList, reportApiList, updateTime }
```

关键点：**解密的最后一跳在 native**。`TlsPlusManager` 的 `c/c1/d/d1/d2/e/f/f1/f2/g` 全部 `code=False`，
实现在 `libsswanutils.so`（559 KB）。该库字符串表被压得很干净（1246 条，无 `AES`/`key` 类明文），
静态取键需要 ARM64 反汇编或 Unicorn 仿真。

隧道是双栈：sing-box（`io.nekohasekai.sfa.bg.VPNService`、`libbox.so` 396 个 JNI）与私有代理
（`com.free.connect.ProxyService`，`startProxy(String,String,int,int,int,String,int,int,String,String)` 是 native，
实现在 `libuchannel.so` / `libnms.so`）。服务端配置键：`key_server_ip`、`key_server_port`、`key_server_mode`、
`key_new_protocol`、`key_protocol_ctrl`、`key_up_proxy_uuid`。

`assets/p2p.json` 是 BT 客户端黑名单（uTorrent 等），`assets/dic` 是混淆字典，都不含节点。

结论：结构最清晰，只差一把 native 密钥。拿到 `TlsPlusManager.f` 的密钥后，`ApiConfig` → 初始化接口 → `NodeBean`
是完整可复现链路。

## 4. com.vpnmasterx.fast（VPN Proxy Master 2.3.6）

```
versionName 2.3.6 / versionCode 23031701 / minSdk 24 / targetSdk 33
dex 3 / .so 14
```

协议层是 protobuf，`classes2.dex` 的 `com.vpnmasterx.networklib.message`：

```
VpnGetServersReq/Resp · VpnGetConnectionConfigReq/Resp · VpnGetServerAuthReq/Resp
VpnResolveServerReq/Resp · VpnGetConfigTemplatesReq/Resp · VpnReportServerStatusReq/Resp
TVpnNode · TVpnServer · TConnectionConfig · TConfigTemplate
```

加密在 `libnative.so`（398 KB），导出：

```
Java_com_vpnmasterx_lib_NativeApi_decryptApi([B I I String String J)[B
Java_com_vpnmasterx_lib_NativeApi_decryptData([B)[B
Java_com_vpnmasterx_lib_NativeApi_encryptApi/encryptData
Java_com_vpnmasterx_lib_NativeApi_getAppId/getGuiVerPatch/getUserAlias/md5/sha1
```

算法已确认是 **AES/CFB/NoPadding**：`libnative.so` 的字符串表里直接有
`javax/crypto/spec/SecretKeySpec`、`AES/CFB/NoPadding`、`SHA1`，
它是通过一个叫 `natiflect` 的 C++ 反射桥回调 Java `Cipher`。

Java 侧包装是 `com.vpnmasterx.networklib.EncryptUtil`：

```
decryptData(String)  -> Base64.decode(s, 3) -> NativeApi.decryptData(bytes) -> new String(bytes, <动态字符集名>)
decrypt(int,int,String,String,long,String) -> NativeApi.decryptApi(...)
```

`<动态字符集名>` 由 `Ls8/d.a(byte[],byte[])` 算出，实为 `Lr4/a.b(byte[],byte[])` 的逐字节 XOR
（`<clinit>` 里 `{0x1d,0x45,0x07,0x4d,0x05,0x41}` XOR `{0x73,0x24}` = `"native"`，同一手法）。

另有 MT 管理器对抗：`libstub.so`、`libSignatureKiller.so`、`assets/SignatureKiller`。

结论：协议与数据结构最规范，密钥仍由 native 计算，同样需要动态取键。

## 5. com.starnest.vpnandroid（VPN v206）

```
versionName 206 / versionCode 206 / minSdk 26 / targetSdk 36
dex 3 / .so 7
```

只有 ICS OpenVPN 一套内核（`de.blinkt.openvpn.core.OpenVPNService`），
manifest 里另有 `VpnConnectionExpiredReceiver`、`PasswordBackupService`、`PhotoHiddenBackupService`，
确认是"VPN + 私密相册 + 浏览器"的工具合集模板。

`assets/data`（1.5 MB）与 `assets/data_v1..v13`（合计 6.4 MB）base64 解码后熵 8.00、块对齐，
但**与节点无关**：`assets/rv_binddatas.xml` 与 dex 里 `Lef/h`、`Lef/i` 引用的是 RecyclerView 绑定变量名
`data_v1`，这批文件是广告模板的绑定数据。本项目 `data_v*` 的字段名与广告 SDK 的布局绑定一致。

本轮未在字符串池中找到任何非 SDK 业务域名，节点 API 主机尚未定位。

## 6. 横向结论

**两套后端指纹。** `Proxy Master 5.4.5` 与 `VPN Proxy Master 2.3.6` 属于不同厂商（AllConnect SDK vs vpnmasterx
自有 networklib），但两者在 dex 里引用的 Bigo 广告域（`api.inmense.site` / `api.dollphoin.site` /
`api.kickoffo.site` / `api.keysuccess.site`）实测返回**同一格式**的 `405 {"msg":"invalid uri"}`，
说明它们共用同一家广告变现中台。这不等于共用节点后端，排查时不要把两者混为一谈。

**四个样本都不走"接口直接吐标准订阅"路线。** 与 `FastVPN-Astro-ProxyPool`、`EdgeVPN-ProxyPool` 那批
（一条 `GET /api/getNewServers` 拿 46 节点）相比，本批的难度整体上移了一档：节点全部在账号态后，
密钥全部下沉到 native。想复用旧流水线，缺的是动态取键这一步。

## 7. 本轮阻塞与下一步

阻塞点只有一个：**没有可用的 Android 环境**。本机 `adb devices` 为空，`~/.android/avd` 为空，
没有 emulator 二进制。四个样本的最后一公里（native 密钥、账号态节点接口）都需要它。

按收益排序的下一步：

1. 起一个可 root 的 x86_64 AVD（API 30 左右），装任一 APK + frida-server（版本必须与
   `pip show frida` 一致，本机是 16.5.9）。
2. 对 `com.free.vpn.proxy.master.app` hook `Lcom/hotspot/vpn/tls/TlsPlusManager;->f` 与
   `Lg5/b;->a()`，直接拿到解密后的 `ApiConfig`；再 hook `Lc5/f;->a()` 拿 `supertop_api_config` 原文。
3. 对 `com.vpnmasterx.fast` hook `Lcom/vpnmasterx/networklib/EncryptUtil;->decryptData`，
   直接拿明文响应，绕过 native 取键。
4. 拿到节点后，本仓库的 `nodes.json → mihomo/sing-box → proxies.txt` 流水线可直接复用。
## 8. 追加：native 层静态还原（同日）

### 8.1 动态环境的尝试与硬阻塞

按计划装了 Android SDK（cmdline-tools + platform-tools + emulator 37.3.9）与
`system-images;android-30;google_apis;arm64-v8a`（3.2 GB），手写 AVD 后启动：

```
FATAL | Avd's CPU Architecture 'arm64' is not supported by the QEMU2 emulator on x86_64 host.
        System image must match the host architecture.
```

emulator 37.x 的 frontend 直接拒绝在 x86_64 主机上跑 arm64 镜像（尽管包内确实带了
`qemu-system-aarch64.exe`）。而四个样本里三个（`com.free.vpn.super.hotspot.open`、
`com.free.vpn.proxy.master.app`、`com.vpnmasterx.fast`）只打包了 arm64-v8a/armeabi-v7a，
x86_64 AVD 上 `System.loadLibrary` 直接失败。MuMu/LDPlayer 的官方安装包直链不可枚举，
未能在本轮安装。

结论：官方 AVD 路线对这批样本不可用，除非改用带 ARM 转译的第三方模拟器（MuMu 12 / 雷电 9）
或接真机。本轮改走纯静态 native 还原。

### 8.2 com.vpnmasterx.fast —— 报文加密已完整还原

`libnative.so` 的符号表未做混淆，直接给出调用图：

```
Java_com_vpnmasterx_lib_NativeApi_decryptData      @0x37308
  -> to_data_password(env)                          @0x36338
       snprintf(buf, 200, "%s_%s",
                "d770ff1b0e4238377b06952b448c99d7b42c5caa",
                "aca8fb1bed0a6547bc5a422eb9a966aa")
       MessageDigest.getInstance("SHA1") -> digest -> "%02x" -> 取前 32 字符
  -> mB1wU3gS3h(env, jbyteArray, jstring)           @0x353ec
       SecretKeySpec(password.getBytes("UTF-8"), "AES")
       Cipher.getInstance("AES/CFB/NoPadding")
       IvParameterSpec(.data:0x64010)
       Cipher.init(2, key, iv).doFinal(data)
```

常量与结果：

| 项 | 值 |
|---|---|
| seed | `d770ff1b0e4238377b06952b448c99d7b42c5caa_aca8fb1bed0a6547bc5a422eb9a966aa` |
| SHA1(seed) | `c4acc9814f5a024ad6c3549f4e42eb96a41c01e5` |
| AES key | `c4acc9814f5a024ad6c3549f4e42eb96`（32 ASCII 字节，AES-256） |
| IV | `000102030405060708090a0b0c0d0e0f`（.data:0x64010） |
| 模式 | AES/CFB/NoPadding，128-bit 段，DECRYPT(2) |

实现见 `tools/decrypt_vpnmasterx.py`，已完成 encrypt→decrypt 往返自洽校验。
另：`decryptApi([B I I String String J)` 走的是带外部 key 的第二分支，与 `decryptData`
不同源，节点接口用的多半是它——那两枚 String 来自设备侧，需要动态取值。

`networklib` 的协议是 **单端点 + method 码 + protobuf**：
`VpnGetServersReq.getMethod()=100`、`VpnGetConnectionConfigReq.getMethod()=103`，
其余为 101/102/104 系列。传输层 `networklib.d.a/b` 本身是 native。

本轮未能在 dex 字符串池里找到任何非 SDK 域名（唯一看着像域名的 `rx3.io` 实为
RxJava3 的系统属性键 `rx3.io-priority`/`rx3.io-keep-alive-time`，不是主机）。
基址由运行时构造，静态侧尚未定位。

### 8.3 com.free.vpn.proxy.master.app —— 下一块硬骨头

`libsswanutils.so`（559 KB）符号表未彻底剥离，可以直接看到自研实现：

```
_ZN3AES12EncryptBlockEPKcPc      # 手写 AES 单块
_ZN3AES3XorEPcPKc                # AES 层之外再叠 XOR
```

即 `TlsPlusManager.f(Context, String)` 用的不是标准 JCE，而是**自带 AES 实现 + XOR 变换**。
这比 `libnative.so` 那种「native 调 Java Cipher」的形态更封闭，还原需要读懂
`AES::EncryptBlock` 的轮密钥编排。符号在，路是通的，但工作量明显更大。

## 9. 追加：三套 native 密钥链的静态还原结果

### 9.1 com.vpnmasterx.fast —— 完成（详见 8.2）

### 9.2 com.free.vpn.proxy.master.app —— JNI 表已还原，卡在签名门禁

`libsswanutils.so` 没有 `Java_*` 导出，走 `RegisterNatives`。`JNI_OnLoad @0x2aaa0` 里有大量
整数混淆做花指令，但注册点干净：

```
0x2b798  RegisterNatives(env, clazz, table = .data:0x931d0, 9)
```

`.data` 里 9 条 `JNINativeMethod{name, sig, fnPtr}`，指针全部是 `R_AARCH64_RELATIVE`，
按 addend 解出来：

| Java 方法 | 签名 | native 实现 |
|---|---|---|
| `c` | `(Landroid/content/Context;)Ljava/lang/String;` | `mth3` |
| `c1` | 同上 | `mth31` |
| `d` | `(Landroid/content/Context;Ljava/lang/String;)Ljava/lang/String;` | `mth4` |
| `d1` | 同上 | `mth41` |
| `d2` | 同上 | `mth42` |
| `e` | 同上 | `mth5` |
| **`f`** | 同上 | **`mth6`** |
| `f1` | 同上 | `sub_4F622` |
| `f2` | 同上 | `sub_4F621` |

`mth6 @0x295c4` 的动作先取 `getPackageManager` → `getPackageInfo` → **`signatures`**
（`[Landroid/content/System/Signature;`），再算一个 32 位值，然后：

```
0x297b8  cmp w22, #0xE8A612C2
0x297bc  b.ne → 返回 null
```

即 `TlsPlusManager.f()` **只在签名指纹命中 `0xE8A612C2` 时才解密**，否则返回 null。
这个原签名不在 APK 里：包内的 `libSignatureKiller.so` 用的是 `xhook`
（`xhook_register` / `xhook_refresh`），靠运行时 hook `getPackageInfo` 伪造，不携带证书字节。
静态路线到此为止——不是算法看不懂，是缺输入。

### 9.3 com.free.vpn.super.hotspot.open —— key 拿到了，但对不上 server 密文

`libnative-legacy.so` 只导出一个 JNI：`NativeLegacy.getKeyBytes`。`@0x1afb0` 的写法很简单：

```
adr x24, 0x10280;  w25 = 0xA5
for 3 blocks:  out[i] = rodata[0x10280 + i] XOR 0xA5
```

`.rodata:0x10280` 起 24 字节异或 0xA5 后是纯 ASCII：

```
01fb3864 e37eb5d4 1f1a373e          ->  "01fb3864e37eb5d41f1a373e"（24 字节，AES-192 长度）
```

紧随其后的 `0x10298` 是明文 `Pure vir`（没被异或），说明前 24 字节才是密钥区。

拿这把 key 对 `assets/server`、`assets/server_files/server`、`assets/server_files/server_IR`
跑 AES-192 的 ECB / CBC / CFB / OFB × 偏移 0/8/16，全部失败。两个 `server` 文件 base64
解码后长度 ≡ 8 (mod 16)，`server_IR` 恰好 ≡ 0 (mod 16)，格式本身不自洽，说明这批
资产的封装不是「纯分组密文」，要么另有流式变换，要么根本是另有用途的历史文件
（dex 里不存在 `server_files` 字面量，Java 层从未按该路径打开过）。

`getKeyBytes` 实际服务的多半是 API 请求签名，不是这两组资产。

### 9.4 静态路线的边界

三个样本的 native 都没加壳、符号表都在，读得进去。真正的墙不是混淆，是**输入**：

- `Proxy Master 5.4.5` 要原厂商签名证书（APK 里没有，靠 xhook 伪造）
- `VPN Proxy Master 2.3.6` 的 `decryptApi` 要设备侧 key（`decryptData` 的常量 key 已拿到，
  但节点接口走的是前者）
- `SuperUnlimited` 的节点在账号态后

这三条都指回同一个结论：**要节点必须有能跑起来的环境**，静态能给的到此为止。
